## Concept

A hosted app for building and maintaining a **structured knowledge graph** — entities plus typed,
nestable relationships — that you create and keep current by *talking to an AI agent* (via MCP), not
just by hand-editing. Daniel's World Train series bible is the first instance, but that is a
deployment detail, not the product. Accessible from any device, persistent, multi-tenant.

---

## Product Direction

> Captures the strategic pivot. Sequenced work lives in [docs/roadmap.md](docs/roadmap.md).

**Positioning.** Kol Emet is an **AI-maintained knowledge graph for interconnected systems** — not a
documentation/prose tool. The durable differentiator is not "chat with an AI to write docs" (table
stakes); it is a **structured entity + relationship graph that an agent builds and maintains for you**
through the MCP tools, with manual editing always available. Most prose docs don't need this; systems
with many interconnected parts do.

**Beachhead → expansion.** Lead with **worldbuilding** (already works; a forgiving, underserved
proving ground for the graph+agent loop) and generalize the engine underneath it. The commercial
expansion is **software/system architecture** (teams, seats, B2B budget). Worldbuilding-first
*de-risks* architecture because the generalization work — user-defined entity types, templates,
graph generation — is exactly what carries the engine across.

**The hook (two stages).** (1) *Assistant* — the agent helps you build the graph one piece at a time
(largely built today). (2) *Generator* — point it at unstructured input (a braindump, a doc, or for
software: a **repo / OpenAPI spec / compose / k8s / DB schema**) and it proposes the whole graph. The
generator is the real draw; the software vertical's inputs make it a far stronger, more defensible
demo.

**Never stale, always reviewed.** The graph is *derived* from its sources: when a source changes, the
system detects drift and **proposes** an update — the model never goes out of date. Every generated or
drift-driven change lands as a **reviewable diff a human accepts** (no silent bulk writes). Drift
detection, version control, and this approval step are **one mechanism**: a proposed change is a
*pull request against the graph*.

**Git-native / repo-resident (dual-mode, DB-canonical first).** The graph gets a canonical
serializable form; a Git connector round-trips it into the customer's repo so it is versioned by
*their* Git, reviewed in *their* PRs, updated by *their* CI — "it lives in your repo and versions
itself." Storage stays DB-canonical initially (keeps SaaS + worldbuilding simple); repo-canonical is
an open question to revisit for pure-dev customers.

## Data Model

> This section captured the original single-entry shape. The model has since evolved — long-form
> content moved into an ordered `blocks` array (no more `body`), and relationships and open questions
> became their own collections. **See [docs/data-model.md](docs/data-model.md) for the current
> schemas.** Summary of the central `Entity` document:

- `_id` — MongoDB ObjectId (primary key)
- `title` — string
- `category` — one of: Characters, Worlds, Organizations, Lore & Mechanics, Timeline, Open Questions
- `summary` — one-line description
- `tags` — array of strings (queryable)
- `blocks` — ordered content blocks `{ _id, type, order, data }`; `type` ∈ text, timeline_event, attribute, quote, gallery
- `relationships` — refs → `RelationshipGroup` (back-reference; groups are the source of truth)
- `open_questions` — refs → `OpenQuestion`
- `workspaceId` — multi-tenancy key; enforced per request (`resolveWorkspace`)
- `createdAt` / `updatedAt` — timestamps

Supporting collections: `RelationshipGroup`, `RelationshipType`, `OpenQuestion`, `ChangeLog`
(30-day TTL audit trail), `Conversation` (saved AI chats), `User`, `Settings`.

## Decision Log

*Running notes on key technical decisions and the reasoning behind them. Add entries as the build progresses.*

- **MongoDB over SQLite** — Consistent with Daniel's existing Steadfast Code projects. Tags modeled as arrays rather than comma-separated strings, which is more natural in MongoDB and easier to query.
- **Block-based content over a flat `body` string** — Entry bodies became an ordered `blocks` array (text, timeline_event, attribute, quote, gallery). Structured, individually reorderable content the frontend and MCP can manipulate per-block; the legacy `body` field was migrated out and dropped.
- **Relationships as groups, not directed edges** — A relationship is a `RelationshipGroup` with a member list; a pairwise link is just a two-member group, and families/factions are many-member groups. Members use a unified array with a `refModel` discriminator (`Entity` | `RelationshipGroup`), so groups can nest and array position encodes order. Chosen over dual entity/subgroup arrays to keep ordering and traversal uniform. The group's `members` array — not the back-reference on `Entity` — is the source of truth.
- **Session + passkey auth over "simple bearer token"** — The original private-tool plan called for a bare bearer token. Since the real target is a multi-tenant SaaS product, auth moved to session cookies (bcrypt) plus WebAuthn passkeys, with open registration; the bearer token remains only for MCP/programmatic access.
- **Change history with a 30-day TTL** — Entity writes append to a `ChangeLog` with a pre-change `snapshot` (enables rollback) and an `actorType` (`user` vs. `mcp`) so history can distinguish human edits from AI/background writes. TTL-expired after 30 days: this is recent undo/audit, not permanent provenance.
- **MCP over HTTP + OAuth, not stdio** — The standalone stdio MCP process was replaced by a Streamable-HTTP endpoint (`/mcp`) inside the Express app, with an OAuth authorization-code + PKCE flow so the Claude.ai connector can authorize. Keeps MCP on the same deployed API and auth surface rather than a separately-run local process.
- **AI chat via an OpenAI-compatible client** — In-app chat and MCP responses route through a provider registry (`aiProviders.js`) using the OpenAI client shape, with per-provider base URLs (currently xAI/Grok, OpenAI, Gemini). Keeps the layer provider-agnostic; a local Ollama provider drops in the same way.
- **Reposition as a knowledge-graph platform, not a documentation tool** — The differentiator is the structured entity + relationship graph maintained conversationally by an agent, not AI prose assistance (which is now table stakes). "Documentation" undersells and mis-targets it; "AI-maintained knowledge graph for interconnected systems" is the product. See Product Direction.
- **Worldbuilding as beachhead, architecture as expansion** — Lead with worldbuilding (already works, forgiving, underserved) to prove the graph+agent loop; expand into software/system architecture for the real market (teams/B2B). Rejected both "stay niche" (too small) and "general documentation tool" (undifferentiated, brutal incumbents). The generalization work is shared between the two, so beachhead-first is cheap.
- **User-defined entity types over a hardcoded enum** — The `category` enum (Characters/Worlds/…) will become per-workspace user-defined types so the engine serves any domain. `RelationshipType` is already data-driven, so relationships generalize for free; templates (entity-type + relationship-type bundles) become the multi-vertical mechanism.
- **Generator with a human-approval diff; no silent bulk writes** — Bulk graph generation and drift-driven updates always land as a reviewable draft a human accepts. Framed as a *pull request against the graph*, this unifies generation, drift detection, and versioning into one mechanism.
- **Never-stale via continuous sync** — The graph is derived from connected sources; source changes are detected and proposed as updates, so the model doesn't rot. Directly targets the failure mode (staleness) that kills documentation products.
- **Git-native, dual-mode storage — DB-canonical first (decided 2026-09-03)** — The graph gets a canonical serializable form; a Git connector round-trips it into the customer's repo (versioned by their Git, reviewed in their PRs, updated by their CI). **MongoDB is the source of truth**; the Git connector is a round-trip, not the store. This keeps multi-tenant SaaS and non-technical (worldbuilding) users simple. Whether to ever make a repo *canonical* for pure-dev customers is left open. **Consequence:** the `ChangeLog` 30-day TTL must be lifted for versioned workspaces — history becomes the product, so it can't expire. (Supersedes the TTL rationale above for versioned workspaces.)
- **Structure ChangeLog/generator-diff records to be fine-tune-ready (decided 2026-09-03)** — Long-run parallel track: fine-tune a self-hosted open-source model on our own accept/edit/reject signal (structured extraction, MCP tool-calling for graph maintenance) rather than hand-authoring training data. This only works if `ChangeLog` entries and Generator v1's approve/edit/reject decisions are captured as structured input→proposed-output→accepted-output triples, not free text. Not on the launch critical path — cloud providers (OpenRouter/native) stay the default — but the data shape should be decided now since it's cheap today and expensive to retrofit later. Self-hosted is a genuinely offerable provider option once tuned, per the existing Ollama-compatible provider registry, but never the default backing paying customers. The self-hosted target is the `steadfast-ai` box (own repo at `C:\repos\steadfast-ai`; GTX 1080 Ti / 11GB VRAM, Ollama behind an OpenAI-compatible gateway on the tailnet).
- **`Draft` is the training corpus, not a work queue (decided 2026-09-06)** — Generator v1's `Draft` collection has **no TTL** anywhere, unlike `ChangeLog`'s 30 days: `ChangeLog` is undo, `Draft` is the fine-tune asset from the entry above and must be permanent. Three consequences follow. `DELETE /drafts/:id` is a soft `status: 'discarded'`. A rejection never deletes the item — the negative example is the most valuable label and the easiest to lose. And `accepted` is written at **decision** time rather than apply time, copied verbatim from `proposed` on a plain accept, so a draft reviewed in full and then abandoned (the common outcome) still yields a complete labelled set. Daniel's product calls, 2026-09-05: account deletion **hard-deletes** drafts, and signup **discloses** that reviewed generations may be used to improve the product, with **no opt-out on the free tier**. Hard delete and the disclosure copy are not yet built — they are the open items this entry creates.
- **A total AI allowance per workspace, not a daily cap (decided 2026-09-05)** — Metering is per workspace in **micro-dollars** (integers; float cents drift when decremented on every call). Daniel chose a total trial budget with **no time limit** over a daily rate after cost modelling: measured runs vary ~6x ($0.011–$0.15), so a run cap prices nothing, and the audience works in bursts — a free Saturday with three chapters of notes is the exact session a daily cap blocks, while worst-case exposure is identical either way. Default grant **$3.50** (`AI_TRIAL_GRANT_MICROS`). Generation is a **capped trial**; the non-AI product stays free forever. The allowance covers everything on a provider we pay for — generation, chat, memory extraction — including **self-hosted, which is cheap but not free** (a derived electricity rate, ~85x cheaper on input than Sonnet: Daniel's call, "it's costing me electricity"). It deliberately excludes **MCP**, where Claude.ai runs inference on the user's own subscription. **Consequence:** an exhausted allowance currently blocks self-hosted runs too, so the "trial ends, generation gets slower rather than stopping" fallback needs its own decision — deferred.
- **The human label and the system outcome are separate field groups with separate writers (decided 2026-09-06)** — On a draft item, `decision`/`decisionVia`/`decidedBy`/`decidedAt`/`accepted` are written **only** by the decision routes, and `applyState`/`resultId`/`changeLogId`/`applyError`/`appliedAt` **only** by the applier, which rejects those keys with a 400 if they appear in a request body. So an apply failure can never overwrite the record that a human said yes, and a client cannot forge what happened to a change. This is what makes decisions and Apply safely separable, which in turn is what lets a reviewed-then-abandoned draft still be a complete training example. Related: applied writes log with `actorType: 'generator'` and an `origin` back-reference to the draft item, not as ordinary user edits — a 30-item apply must not be indistinguishable from thirty hand edits.
- **Exports pseudonymise and refuse; the exporter takes no join (decided 2026-09-06)** — A draft exports to one JSONL line in which **no ObjectId survives**: references to things created by a sibling item become `local:<localKey>` (the form a model should learn to emit), everything else a keyed HMAC pseudonym that is deterministic, so a corpus stays joinable without ever holding a real id. `EXPORT_HMAC_SECRET` has **no default** — a shared fallback key would make the mapping reproducible by anyone with the source, and ObjectIds are partly a timestamp and a counter. A raw id surviving the mapping **fails the export**, naming the field, rather than being scrubbed by a blanket regex: a scrub would quietly paper over a field the mapper forgot and surface months later as an unexplained id in the corpus. The load-bearing constraint is that `exportDraft` runs **zero queries** — items are embedded in the draft precisely so this holds. If exporting ever needs a join, the schema is wrong and that is the bug to fix.
- **The Express app is a factory; `index.js` is only a bootstrap (decided 2026-09-08)** — Middleware, session config and every route mount moved to `server/src/app.js` as `createApp({ sessionStore })`; `index.js` keeps only `dotenv`, `mongoose.connect` and `app.listen`. The session store is the one injectable seam, defaulting to the deployed `MongoStore`, so a test can pass an `express-session` MemoryStore and drive the **real** app over HTTP with no database — as `tests/http/oauth.test.js` does for the OAuth PKCE flow. Chosen over exporting a pre-built `app` singleton (which constructs a Mongo-backed store at import time, so importing it in a test already reaches for the database) and over faking routers (which tests the mock, not the mount order that decides whether `requireAuth` actually guards a route). **Consequence:** anything added to the app must be mounted inside `createApp`, and mount order stays load-bearing — `requireAuth` before `resolveWorkspace` is what makes an anonymous request 401 rather than a workspace lookup.
- **Tests run against a real mongod, one per test file (decided 2026-09-08)** — `server/tests/helpers/db.js` starts an in-memory `mongodb-memory-server` rather than mocking Mongoose, so schema enums, defaults, casting and indexes are exercised as they run in production; the alternative (stubbing the model layer) would test the mock and pass through exactly the typo'd `category` the enum exists to stop. The URI comes from `MongoMemoryServer.getUri()` and never from the environment, so no stray `MONGO_URI` can point a run that deletes every document at a real database. `node --test` gives each file its own process, so the module-level server singleton is per-file by construction and files stay isolated. `clear()` drops collections **and resyncs indexes**: a dropped collection takes its indexes with it and Mongoose builds them only once per model, so without the resync a later test of `User.email`'s unique constraint would run against a collection that no longer has the index enforcing it, and pass for the wrong reason.
- **Config-dependent auth gates fail closed in production, open in dev (decided 2026-09-09)** — `/mcp` read an unset `MCP_BEARER_TOKEN` as "dev mode: no token required", which is right on a laptop and catastrophic on a deployed box: `/mcp` is the second front door into tenant content and the only one not behind `requireAuth`, so a forgotten variable published every tool on it unauthenticated. The gate now decides once at module load from `MCP_BEARER_TOKEN` + `NODE_ENV` and, when the token is unset **and** `NODE_ENV=production`, answers `503 {"error": "MCP not configured"}` to everything and logs the reason once at startup. 503 rather than 401 on purpose: this is a misconfigured deployment, not a caller who forgot a credential, and the two need to be distinguishable in a log. Chosen over requiring the token in every environment (breaks local development against `.mcp.json`, which is the only way the endpoint gets exercised by hand) and over refusing to boot (one unset variable would take the whole API down with it, including the REST routes that are correctly configured). `requireAuth` needed no equivalent change — its token is compared strictly against a parsed string, so an unset variable is a value no request can produce — and `server/tests/unit/requireAuth.test.js` now pins that, including the `BEARER_TOKEN=` (empty string) case that a half-filled `.env` produces.
- **Account deletion is ordered, not transactional, and refuses shared memberships (decided 2026-09-10)** — `deleteAccount(userId)` in `server/src/lib/accountDeleter.js` implements Daniel's 2026-09-05 hard-delete call as a library function; the route, confirmation UI and signup disclosure copy are still open. It **refuses on any membership the user does not solely own**, co-owner included, not just editor/viewer: deleting would leave that workspace pointing at a user who no longer exists, and ownership transfer is a product decision nobody has made. A refusal deletes nothing and returns the memberships. A solely-owned workspace is deleted even when others are members of it, as the queue item specifies. It is **ordered rather than transactional**: transactions need a replica set, the test mongod is standalone, and an Atlas-only code path would ship untested. Content goes first, then the workspace documents, then the user, so a failure part-way leaves the user and their workspaces findable and a re-run finishes the job (the test pins this by failing one model's `deleteMany` mid-run). Content is swept again once the workspace documents are gone, catching writes from requests that resolved the workspace while the first pass ran. The workspace-scoped model list is explicit, and a test fails if a model with a `workspaceId` path is missing from it. User-keyed data goes too: `UserMemory`, and `Conversation` by `userId`, which also catches pre-tenancy rows. `Settings.mcpUserId` is cleared if it points at the user. Log lines carry ids, never the email, because logs outlive the account.
- **Account deletion re-authenticates, checks the typed email on the server, and is session-only (decided 2026-09-10)** — `DELETE /auth/account` is the one caller of `deleteAccount()`. A live session does not reach it alone: the body must carry the current password, or a passkey assertion against a single-use challenge from `POST /auth/account/passkey-challenge` (its own session key, so a sign-in challenge cannot be spent on deletion), plus the account's email. The **email check is server-side**: the client never learns the address (`GET /auth/me` returns only `{ authenticated }`), and enforcing it in the API means a script or a forged request has to repeat it too. It is **session-only**: `requireActor` also admits the MCP bearer token, a single secret shared with an AI connector, and ending an account is not something a connector gets to do on a user's behalf, password or not. A failed re-authentication is **403, not 401**, because the session is still good and a 401 reads to a client as "signed out". Success destroys the session in the store, not just the cookie, and clears the cookie with the attributes it was set with, since a bare `clearCookie` does not match the domain-scoped production cookie. Known gaps: the user's *other* sessions cannot be found by user in the store, so they outlive the account holding a dangling id (every tenant route refuses them, and `GET /auth/me` answered 200 until **KOL-038 below** closed it 2026-09-17 by checking the id against the users collection and ending the session it finds dangling); and the password check was not rate-limited (closed by KOL-035 below, which throttles it per account).
- **`EntityType` registry ahead of the enum, with in-use types frozen (decided 2026-09-10, KOL-020)** — Phase 6 step 1 adds the per-workspace `EntityType` registry and `/entity-types` CRUD, seeded with the six current categories at registration (and by `scripts/seed-entity-types.js` for older workspaces), while `Entity.category` keeps its enum and nothing reads the registry yet. Because entities reference a type by *name*, two choices differ from the `RelationshipType` it mirrors: names are **unique per workspace, case-insensitively, by index** (not only by the route's pre-check, which a concurrent create could slip past), and a type that any entity in the workspace uses **cannot be renamed or deleted (409)** for now. The build plan's rename answer is a cascade to `Entity.category`, but with the enum still in force a cascade could only write names the schema rejects on those entities' next save; refusing keeps registry and data consistent until step 2 drops the enum and brings the cascade. Colours are stored as the client's `{ bg, text }` pill pair rather than the plan's single `color`, so the six defaults carry over unchanged.
- **The registry gates category writes alongside the enum (decided 2026-09-12, KOL-022)**: The KOL-020 freeze did not deliver "cannot drift apart". It only guarded renames and deletes, so a deleted or renamed-away type could still be written to an entity, and a type whose name was not an enum value could never be used. The fix has four parts:
  - **Write-time check.** `Entity.category` and `RelationshipType.sourceCategory`/`targetCategory` must name a type in the writer's workspace. A mongoose validator (`lib/entityTypeRegistry.js`) does the check, so it covers every write path the enum covers: REST, MCP, draft apply and rollback. An update whose filter names no workspace is refused rather than let through.
  - **Enum names only.** While the enum stands, a type's name must be one of its values, matched case-insensitively and stored in its spelling.
  - **Relationship types count as uses.** They now block a rename or delete, alongside entities.
  - **Pre-registry fallback.** A workspace with no types at all predates the registry, or its seeding failed. It is checked against the enum alone until backfilled, so a workspace that was never backfilled keeps working. Deleting a workspace's last type is refused, so a user cannot switch the gate off by emptying their registry.
  
  **Rejected alternative:** dropping the enum now, which would make custom names usable. That is Phase 6 step 2. The client, the MCP tools and the generator still list the six built-ins, so custom types would be writable only through REST and invisible in the UI. Phase 6 timing is also Daniel's call.
  
  **Known gap:** an entity write and a type delete that interleave can still slip past both checks. There is no transaction around the pair.
- **Late writes to a deleted account's user-keyed data delete themselves (decided 2026-09-12, KOL-023)**: The second sweep narrowed the concurrent-write window but did not close it. A write that landed after the last sweep stayed for good, because a re-run finds nothing left to sweep. Memory extraction is the clearest case. It runs after the chat reply, makes a model call that takes seconds, and then inserts `UserMemory`, which can happen after the account is gone. The fix has two halves:
  - **The writer writes, then checks.** `UserMemory` and `Conversation` have a schema plugin (`lib/ownerGuard.js`) that looks up the `User` *after* each insert and deletes the rows if the user is gone. The discarded write rejects with `OwnerGoneError`. Checking before the write cannot work, because the model call sits between the check and the write. A plugin rather than a helper means every insert path is covered, including ones not written yet.
  - **The deleter deletes, then sweeps.** After deleting the `User`, the deleter sweeps both collections by `userId` again. Since the writer checks after writing, whichever side reads second sees the other's write, and no ordering leaves a row behind.

  **Rejected alternatives:** a check before each write (still a race, and each new writer has to remember it); a periodic reaper for orphans (closes the gap only eventually, and this app has no scheduler); transactions (these need a replica set, as before).

  **Known gap (closed 2026-09-16 by KOL-026, below):** the workspace-scoped models do not have the guard yet. A content insert that lands after the workspace's final sweep is still left behind. The fix is the same plugin with `{ path: 'workspaceId', owner: Workspace }`. It is deferred because it adds a read to every content insert, and the tests that create content under made-up workspace ids would need real workspaces first.
- **Passkey ids are stored as the browser sends them, and old double-encoded ones are repaired on use (decided 2026-09-13, KOL-024)**: `@simplewebauthn/server` 13 returns `registrationInfo.credential.id` as a base64url string, and registration base64url-encoded it a second time. Every lookup compares against the browser's id, so no passkey was ever recognized. The id is now stored as-is, and `lib/passkeyIds.js` is the one place that matches stored ids and offers them to the browser:
  - **Both forms match.** Sign-in and account deletion's passkey confirmation accept a stored id in the correct form or the legacy one. The legacy match is exact (`stored === base64url(browserId)`). A match only picks which public key to verify with, and the signature check still decides.
  - **Lazy migration.** A verified assertion against a legacy value rewrites it to the correct form. A failed one changes nothing, so knowing an id is not enough to trigger the rewrite.
  - **Corrected ids in `allowCredentials` and `excludeCredentials`.** There is no browser id to compare with there. A stored value counts as legacy when it decodes to base64url text that re-encodes to itself. A correct id passes that test only if every raw byte is a base64url character, a chance of (1/4)^n for an n-byte id, which is under 2^-32 at the spec's 16-byte minimum.

  **Rejected alternative:** a one-off script to rewrite every stored id. Someone would have to run it by hand against production, and deployed code and data would disagree until they did. The lazy path needs neither. A passkey that is never used again stays in the legacy form, which still matches.

  **Known gaps:** passkeys added before this fix have no `deviceType` or `backedUp`. An assertion carries the backup flags, so KOL-025 can record them at sign-in alongside `lastUsedAt`. Registration also did not refuse a credential id already registered to another account, which the WebAuthn spec says it should (§7.1): `login/begin` lists an account's ids to anyone who knows its email, so a crafted authenticator could register a copy and make the lookup ambiguous — a denial of service, not a takeover, because the signature check still decides. **Closed 2026-09-17 by KOL-036 below**, which refuses a duplicate id with a 409 before storing it; the listing in `login/begin` is unchanged, and the check-then-write race is that entry's own known gap.
- **Passkeys are managed from Settings, session-only, and an account keeps one way in (decided 2026-09-13, KOL-025)**: A passkey lives on the device or password manager that made it, and the only way to add one was the prompt right after signup, so an account made on a desktop could never get one on a phone. Settings → Passkeys now lists them (`GET /auth/webauthn/passkeys`), adds one on the current device (the existing register routes), and removes them (`DELETE /auth/webauthn/passkeys/:credentialID`). Passwordless "Sign in with passkey" without an email is unchanged.

- **Registration's duplicate check asks a wider question than sign-in (decided 2026-09-21, KOL-043)**: KOL-036 refused an already-registered credential id with `User.exists(credentialIdQuery(...))` — the same query sign-in uses. That query is one-directional across the two stored id forms, so the attack it exists to stop was still available, run backwards. An authenticator chooses its own raw credential-id bytes: bytes equal to `utf8(victimId)` are reported by `@simplewebauthn` as the id `legacyEncoding(victimId)`, a different string. - **A caller's search string is escaped before it is compiled, and typed before it is a filter (decided 2026-10-05, KOL-049)**: `GET /entities`, the MCP `search_entities` tool and the chat assistant's local copy of that tool each ran `new RegExp(theCallersString, 'i')` over every title, summary and block markdown in the workspace. `routes/bridge.js` already escaped its own `q` with exactly the character class the three needed; they never got it. Every request ran a bcrypt hash at cost 12 and every success wrote a `User`, a `Workspace` and a whole template seed — 38 relationship types plus starter content — so one unauthenticated client could fill this database and spend this API's CPU as fast as it could post. KOL-035 built the counters and left this out of scope by name ("CAPTCHA or signup throttling"). `createAuthLimiter` now has a fourth counter kind, `signup`, keyed on `req.ip`: 10 created accounts per address per 60 minutes, from `AUTH_LIMIT_MAX_SIGNUPS_PER_IP` and `AUTH_LIMIT_SIGNUP_WINDOW_MS` or the `authLimits` option `createApp` already threads.

The workspace rollback path deliberately stays counted — by then the hash and two writes are already paid for, and that cost is the thing being bounded.

- **A tag is edited where it lives — on every entity at once (decided 2026-10-06, KOL-053)**: `GET /tags` was the whole tag surface, and a tag is nothing but a string in each entity's `tags` array, so a workspace holding `train`, `Train` and `trains` could only be fixed by opening every entity. `PUT /tags/:tag { to }` and `DELETE /tags/:tag` in `routes/tags.js` do it in one request, scoped to the caller's workspace, and a **Tags** group in Settings lists each tag with its entity count and a rename and remove for each.
  - **A rename merges, and merging is two writes.** `$addToSet` then `$pull`, in that order. Mongo refuses both operators on one field in one update, and the order matters on its own: an entity carrying both the old and the new name must end with exactly one copy of the new one, and reversing the writes would leave it with none. A rename to itself short-circuits to a 200 no-op before the `$pull`, which with `from === to` would strip the tag it just added.
  - **One `ChangeLog` entry per changed entity, awaited before the response.** The point of the feature is that a bulk rename is as reversible as the single edit it replaces: each entity rolls back from its own snapshot through the history route that already exists, and each entry broadcasts `entity:updated` so open clients follow. A single entry for the whole operation would have been cheaper and would have rolled nothing back. Awaited, not fire-and-forget as the entity routes' logging is, so the answer means the trail exists.

Same reasoning as KOL-045's compose-import cap. A workspace that genuinely needs more does it in passes, and the refusal says how many it would have touched.
  - **Counts come from the entity list, not a route.** `GET /tags` answers names; the Settings group derives `{ name, count }` from the entities the layout already holds, and refetches after a change. A `/tags?counts=1` would have been a second aggregation over the same data the client has in memory.
  - **Out of scope, still open:** tag colours and descriptions; renaming a tag from the entity editor; an index on `Entity.tags` (an Atlas change) — the bound is what keeps the unindexed scan honest for now; and any change to the tag pill row.

- **A re-import updates the link it created last time, rather than stacking a second one (decided 2026-10-06, KOL-054)**: `applyRelationship` always did `RelationshipGroup.create(...)`, and nothing looked for a group that already held those members under that label — so re-importing an unchanged docker-compose or OpenAPI file, the ordinary case and the one `source.textHash` exists to recognise, added a second "Depends on" group for every edge it had found the first time, and each entity's Relationships section showed the same link twice. KOL-045 recorded this as accepted, on the grounds that recognising an existing group is drift detection. Recognising one is not: a proposed relationship whose resolved member ids and label match a group the workspace already holds is now `op: 'update'` with `proposed.targetGroupId` and `matchedBy: 'same-members-and-label'`, and the applier updates that group in place.
  - **Matched where the entities are matched, not in the write.** `draftNormalizer.relationshipGroupMatcher` is called by the normalizer and by both producers, which is what lets the review UI say "updates a link you already have" before anyone applies. A member that only resolves at apply time — a sibling entity the same apply has just created — could not have been matched then, so `applyRelationship` runs the same matcher over the ids it has just resolved. One rule, applied wherever the ids become known.
  - **The match ignores order and roles, and three rules keep it from merging links that are not the same link.** A group that *holds* the proposed members matches, so a group someone has since widened by hand is still recognised — but an exact member set outranks a superset, so a 3-member group never swallows the 2-member edge beside it. Role agreement breaks the remaining ties, so "web calls api" does not match the group recording that api calls web. And a group is claimed by at most one proposal, so two items of one draft cannot collapse into one group.
  - **The update is `$set` on the members the proposal names, and nothing else.** The source file is authoritative about the roles it describes and silent about everyone else, so a member a person added keeps its label, its notes and its place, and the group never shrinks. A role the proposal leaves null says nothing rather than "clear it".
  - **`targetGroupId` travels in the payload, not beside it.** It sits in `proposed`/`accepted` with the members it was matched from, so an edit that re-points the members carries — or drops — the target in the same object; `draftItemSchema` validates it and the applier re-scopes it to the workspace before writing, so an id edited in by hand cannot reach another tenant's group.
  - **Out of scope, still open:** proposing the *removal* of a link that has disappeared from the source (drift detection proper); deduplicating the groups earlier re-imports already stacked; `ChangeLog` entries for relationship writes, which the applier has never recorded; and open-question dedup.

- **A cookie-authenticated write has to come from this deployment's own client (decided 2026-10-07, KOL-058)**: Nothing in `server/src` read `Origin` and nothing carried a CSRF token, while production issues the session cookie with `sameSite: 'none'` on purpose — the client and the API are sibling subdomains — so a browser sent it on cross-site requests. CORS was not the gate it looked like: `express.urlencoded` was mounted on the app, a form-encoded POST is a CORS-*simple* request sent with no preflight, and CORS withholds only the response. An attacker's page therefore reached every cookie-authenticated POST with the victim's session: `POST /entities` creating content, `POST /drafts` spending their AI allowance, `POST /entities/:id/rollback/:logId` and `POST /auth/logout` needing no body at all, and `POST /authorize` re-pointing `Settings.mcpUserId` at whoever was signed in. `middleware/originGuard.js` now refuses an unsafe method from a session caller whose origin is not `CLIENT_ORIGIN` or the API's own, with 403 `{ error: 'CROSS_ORIGIN_REQUEST' }`.
  - **The header check, not a CSRF token.** Every client of this API is either a browser on one known origin or a bearer caller, so `Origin` — which a page cannot forge — is the whole fix, and it costs no per-request state, no token endpoint and no form plumbing. `sameSite: 'lax'` was the other option and is not available: it would break the cross-subdomain deployment this product ships as.
  - **Mounted after the session middleware and ahead of every router.** Not per-route: a route added later would land outside a per-route guard, and the mount list in `app.js` is where that mistake is invisible. PUT, PATCH and DELETE were already safe — they are preflighted — but they are checked too, because "which methods CORS preflights" is not a property this code should depend on.
  - **The API's own origin is allowed as well.** The two OAuth approval pages (`POST /authorize`, `POST /bridge/authorize`) are HTML this API serves and post back to it, so the allowlist is the client plus self. `Referer`'s origin is the fallback when `Origin` is absent; a present-but-opaque `Origin: null` is a refusal rather than a reason to consult a second header an attacker also influences.
  - **A bearer caller is exempt.** MCP and the bridge send a token and no cookie, so there is no session to ride — and `Authorization` is not CORS-safelisted, so a cross-site simple request cannot carry one at all. The exemption keys on the header's presence, not on which token it holds; whether the token is valid is the business of the gates behind this one.
  - **Second layer: no app-wide form parser.** `express.urlencoded` moved off the app and onto the *four* routes that take a form — `POST /authorize` and `POST /oauth/token`, plus the bridge's own issuer at `POST /bridge/authorize` and `POST /bridge/oauth/token` — so a cross-site simple POST cannot form a body any other route will read. Four and not two because the bridge runs a second authorization-code + PKCE flow over the same encoding; with `express.json()` left global an unparsed form body arrives as nothing rather than as a throw, so a parser left behind would have answered 400 `missing required parameters` and killed the bridge connector's code exchange quietly. Each parser is mounted inside its own router, next to its routes, so the bridge stays self-contained.
  - **The suite had to be given an origin.** No test under `server/tests/http` sent an `Origin` and none set `CLIENT_ORIGIN`, so every session-cookie write in it became a 403 the moment the guard mounted. `tests/helpers/origin.js` holds the origin and an `originAgent(app)` that sets it as an agent default; each suite names it in its env block. That is the cost of a header-based gate, paid once.
  - **Out of scope, still open:** a double-submit or synchronizer CSRF token; `sameSite: 'lax'`; the `cors()` wildcard behaviour when `CLIENT_ORIGIN` is unset (logged at light in production, not changed); rate limiting on writes; and login CSRF — `POST /auth/login` and `/auth/register` have no session to ride, so the guard does not check them.

- **A rename does not rewrite snapshots; the restore asks which type to use (decided 2026-10-07, KOL-059)**: KOL-027 recorded this as a known gap. `Entity.category` names an entity type by *name*, renaming a type cascades to everything using it but writes no `ChangeLog`, and the registry is the only gate on category names — so every snapshot taken before a rename still held the old name, and `POST /entities/:id/rollback/:logId` replayed it through `runValidators: true`, caught the `ValidationError` and answered **500** `"Characters" is not an entity type in this workspace`. A permanent, unfixable failure reported as a server fault, with no way for the user to get that version back at all.
  - **Snapshots are not rewritten.** The obvious fix — have the rename cascade also rewrite `ChangeLog.snapshot.category` — was rejected. A snapshot is the audit trail: it records what the entity was when the change was made, and editing history so that a later restore succeeds trades away the one property the trail exists for. The restore is the operation that has to cope, because the restore is where a human is present to decide.
  - **409, not 500, and the stale name is in the body.** The route checks the snapshot's category against the registry *before* the write and answers `409 { error, snapshotCategory, availableCategories }`, writing nothing and recording nothing. 409 because the request conflicts with the workspace's current state and no retry of it will ever succeed; the body names what the version was saved under and every type there is now, so the caller can resolve it in one more request without a second lookup.
  - **`{ category }` in the body is the caller's decision.** It is the one field of a snapshot a rollback will override, and only with a name the workspace has (a name it lacks is 400, naming what was sent). Everything else restores exactly as recorded. That is what makes the version reachable again: it comes back under the type that replaced the one it was saved under.
  - **History flags it ahead of the click, in one registry read.** `GET /entities/:id/history` marks each entry whose snapshot category is gone with `snapshotCategoryMissing: true`, from one `registeredCategories` read for the whole page — a per-entry `isRegisteredCategory` would be fifty identical queries for a full page. `client/src/components/EntityDetail.vue` grew the history list this needs: a flagged row offers the workspace's types from `useEntityTypes` and sends the chosen one, and a 409 arriving anyway (a type renamed while the list was on screen) turns that row into the same picker from the types the refusal named.
  - **Out of scope, still open:** `ChangeLog` entries for the rename cascade itself (one per entity, and a `changeType` the model does not have, so the trail would have to grow a vocabulary before it could record this); the same stale-name failure when applying an old draft item, since `proposed` payloads are training records and are deliberately not rewritten either; and restoring a *deleted* entity, which has no entity to update and is its own item.

- **A delete is undoable while its snapshot lives; the restore recreates at the original id (decided 2026-10-07, KOL-060)**: the KOL-059 entry above left this open. `logDelete` already kept the whole document in the `deleted` `ChangeLog` entry's snapshot for the TTL's 30 days, and the delete broadcast already carried it so another open tab could open a read-only `[DELETED]` panel — but `POST /entities/:id/rollback/:logId` read the live entity first and answered **404** when it was gone. The snapshot could be looked at and never put back, and once the toast was dismissed nothing in the client could reach it at all: the entity was gone from the list, and the history route is keyed by an id the user no longer had. For a wiki whose history view is its whole safety net, an accidental delete was unrecoverable with the data still in the database.
  - **The same route, not a new one.** A `deleted` entry whose entity is gone recreates the document instead of updating one; everything else about the route — the actor, the `{ category }` override, the stale-category 409 — is unchanged. A restore is a rollback to the version before the delete, and splitting it into a second endpoint would have duplicated all of that.
  - **The original `_id`, and the caller's workspace.** It comes back at the id it had, so an open question's `entry_ids`, a bookmarked URL and anything else holding that id resolve again — which is also why the response is **201**: this creates a document. `workspaceId` comes from `req.workspaceId` and never from the snapshot, which is null for one taken before tenancy and would orphan the entity out of every workspace; that is why the existing rollback stripped it, and the restore keeps that rule.
  - **409 when the id is live again, so a restore never silently overwrites.** An entity created at that id since the delete is somebody's current content. The check is `Entity.findOne(scope)` before the write, with the unique `_id` (duplicate key → 409) as the real guard behind it.
  - **`relationships` comes back empty.** The delete pruned the groups the entity was in, so the snapshot's ids name groups that are gone or that no longer list it, and a back-reference cache naming them would be dangling. Re-deriving the edges from the other members is drift detection, not a restore — it needs a notion of what the graph *should* be, which nothing here has. The "Recently deleted" group says so in as many words rather than leaving the user to notice.
  - **A way back that outlives the toast.** `GET /deleted` lists this workspace's `deleted` entries newest first (≤50, no snapshots in the page, ids that are live again dropped, and only the newest entry for an id), flagged with `snapshotCategoryMissing` from one registry read; `client/src/components/RecentlyDeleted.vue` is that list plus a Restore per row, in Settings beside Passkeys, mounted only while Settings shows. A stale row offers the workspace's types the way a stale history row does.
  - **Out of scope, still open:** rebuilding the pruned relationship groups; a soft-delete/archive state on `Entity` (a different product shape — the wishlist's own idea); lifting the 30-day `ChangeLog` TTL, which is what bounds how long a delete stays undoable (KOL-019); bulk restore; and restoring a deleted entity from an `updated` entry rather than the `deleted` one, which stays a 404.
- **`GET /entities` is a projected list; blocks are an opt-in (decided 2026-10-07, KOL-061)**: The list route returned every entity in the workspace as a full hydrated document, `blocks` and all, and the client asks for it unfiltered on load — so the one request that decides how long a workspace takes to open carried the entire text of the wiki, on every load, every second tab and every SSE reconnect, and it is the first request a new tenant makes. Nothing on that path reads block content: the sidebar card renders a title, a category badge and a summary, `useFilters` searches titles, summaries and tags, and the detail panel and the editor both re-read the entity through `GET /entities/:id`. The route now `select()`s the eight fields the list needs and reads `.lean()`, matching the single-entity route; on the test's ~48 KB fixture the response goes from 39,740 to 1,416 serialized bytes. `?include=blocks` returns the old, unprojected shape, so a caller outside this repo is not cut off, and it is typed through `searchTerm` like the filters beside it so a bracketed operator or a repeated parameter cannot opt in on the caller's behalf. The `?q=` keyword clause still matches `blocks.data.markdown`: a projection governs the response, not the query, and conflating the two is the mistake `tests/http/entityList.test.js` exists to catch. **Chosen over** pagination (an envelope instead of an array — its own item, and KOL-049 put it out of scope) and over a `blocks` *preview* field (a second shape of block data to keep in sync, for a card that renders no body text today). **Known gap:** the client's search box still filters in the browser over titles, summaries and tags, so block text is not searchable from the UI at all while the server's `?q=` reads it — a real feature gap, unchanged by this and worth its own item.
- **An `/events` stream is re-validated and capped, not trusted for life (decided 2026-10-07, KOL-062)**: `GET /events` authenticated once with `requireAuth` and then held the response open indefinitely, and the broadcaster stored only `{ res, workspaceId }` per connection. Two consequences for a multi-tenant push channel that carries whole entity documents. A stream outlived its session: after `POST /auth/logout`, or after the account was deleted, the socket kept receiving `entity:created`/`entity:updated` payloads, so a browser on a shared machine that had "signed out" still had the workspace's content arriving. And there was no cap: one valid session could open thousands of streams, each a held socket plus a write every 30 seconds, on the single process every tenant shares. Each connection now records the `userId` and `req.sessionID` it was opened by; the **keep-alive sweep that already walks every client every 30 seconds** asks whether that session is still in the store and closes the ones whose is not, and `POST /auth/logout` / `DELETE /auth/account` close theirs at once rather than leaving up to 30 seconds of pushed content behind. The session lookup is **injected** — `createApp` builds `app.locals.sessionAlive` from the store it already has and the route passes it to `addClient` — so `lib/broadcaster.js` keeps no express-session or Mongo dependency and its unit test keeps driving it with fake `res` objects; it fails **open** on a store error, because a database blip must not be the thing that drops every live stream in the deployment. Account deletion closes by **user id**, not session id: the store cannot be searched by user (the same limit the account-deletion entry records), so the deleted account's other browsers would otherwise have kept receiving until their sessions expired. `EVENTS_MAX_STREAMS_PER_USER` (default 10) refuses a further connection with **one SSE `event: error` frame and a close, at status 200** — an `EventSource` reports a non-200 as an indistinguishable network error, so a status code would reach the browser as "the wifi dropped" and be retried forever. The cap is per user, never global (a global one would hand every tenant a way to deny every other tenant live updates), and the bearer-token path shares one allowance because it shares one credential. **Chosen over** re-authenticating on the broadcast path (a store read per payload per client, on the hot path, to catch something a 30-second tick catches anyway) and over a short-lived stream token the client renews (a second credential shape, and reconnect/backoff work in the client, for the same guarantee). **Known limit, unchanged:** the client map is in-process, so the cap is per API instance and a stream is only swept by the instance holding it — the same bound KOL-035 recorded for the attempt counters, and it moves to shared state with them. Logging is `SSE_LOG_LEVEL` (`off | light | normal | verbose`, default `light`), replacing the unconditional `console.log`s; the light tier says *why* each connection ended, because at the browser a dropped stream and a flaky network look identical. Covered by new cases in `server/tests/unit/broadcaster.test.js` and by `server/tests/http/events.test.js`, which drives real held sockets (supertest buffers a response to completion, and no response here is ever completed).
- **One global keydown listener owns the app's keys (decided 2026-10-07, KOL-063)** — `client/src/composables/useKeyboardShortcuts.js` holds the client's only `window.addEventListener('keydown', …)`, and `WikiLayout` registers the whole set through it as named functions: `/` focuses the sidebar search input (through a `defineExpose`d `focusSearch`, not a DOM query from the layout), `Escape` closes the topmost layer — settings, generator, graph, chat, detail panel, in that order, so repeated presses walk back out — and `n` opens the new-entity editor. Ownership is one rule: a focused `input`/`textarea`/`select`/`[contenteditable]` keeps every key **except** Escape, since every other key is a character it is entitled to and Escape is how you leave the field, and a key held with ctrl/meta/alt is never ours. **Consequence:** GraphView's own global Escape listener (and the `containerRef._keyListener` stash it was cleaned up through) is gone, because two global listeners on Escape meant one press closed the graph *and* the layer under it — the opposite of walking back out; the chain closes the graph instead, and GraphView still emits `close` for its ✕. A component that wants a key from here on either registers it in that set or scopes it to its own subtree, as `GeneratorOverlay`'s `@keydown.esc` does (it fires only while focus is inside the overlay, and closes the layer the chain closes anyway, so a double call is a no-op) and as `EntityEditor`'s tag combobox does — that one `stopPropagation`s while its suggestion list is open, which is what keeps an Escape meant for the list from also closing the panel. Logging is `KEYBOARD_SHORTCUT_LOG_LEVEL` (`off | light | normal | verbose`, default `light`); the light tier names the key, the element it came from and the handler it reached, because a press that went to the wrong layer leaves no other trace. Pinned by `client/src/components/WikiLayout.test.js`, which drives real `keydown` events at `window` from the element that would have focus, plus `grep -rn "window.addEventListener" client/src` naming only the composable.
- **A page of `GET /entities` is an envelope only when one is asked for (decided 2026-10-10, KOL-067)** — KOL-061 took `blocks` out of the list response; the row count was still the whole workspace, on the first request every tenant makes, so a workspace of a few thousand entities still serialized a megabyte of JSON in one go on the single event loop this multi-tenant API shares — one tenant opening a large workspace stalls everybody else's requests. `?limit=` (1–200) now returns `{ items, nextAfter, total }` and **no `?limit=` returns today's bare array, unchanged**. Making the envelope opt-in is what keeps this from being a breaking change: the MCP tools, the chat tool, the graph view and any script outside this repo read the array shape, and a product in pre-alpha gets no notice period for free. The client is the caller that opts in — `loadEntities` walks pages of 200 and clears `sidebarLoading` after the *first* page, so the sidebar paints immediately instead of waiting for the workspace. Paging is **keyset, not `skip`**: `?after[title]=…&after[_id]=…` names a position in the sort, so an entity created while a client is paging does not shift every later row forward one place and make `skip` serve one row twice and drop another. The cursor carries `_id` because titles are not unique and the two rows sharing one would straddle a boundary; the sort therefore became `{ title: 1, _id: 1 }`. A present-but-unusable cursor is **400 rather than ignored** — a silent first page would make a client that pages until `nextAfter` is null never stop. `total` counts the filtered set, not the remainder after the cursor, so it does not shrink as pages advance. `?limit=` is typed through `boundedInteger` in `lib/searchFilter.js`, beside the `searchTerm` rule it mirrors: `?limit[$gt]=1` arrives as an object and `?limit=1&limit=2` as an array, and either reaching `.limit()` is a 500 rather than a page — and `0` passed through would mean *no limit* to MongoDB, the opposite of what was asked. **Consequences:** `Entity`'s index is `{ workspaceId: 1, title: 1 }`, which is not a prefix of the new sort, so the tie-break is still a blocking in-memory sort — extending the index to `{ workspaceId: 1, title: 1, _id: 1 }` is the follow-up, left out here because it is an index change on a live Atlas collection rather than part of the route. And the client's search box still filters only what is loaded (KOL-068 is asking the server); `/conversations`, `/drafts` and `GET /entities/:id/history` already cap at 50 and were left alone.
- **The search box asks the server; the pills stay in the browser (decided 2026-10-10, KOL-068)** — `useFilters` filtered the already-loaded list over `title`, `summary` and `tags`, so the one field a wiki keeps its content in was not searchable from the UI at all: a word that appeared only in a text block found nothing in the sidebar while `GET /entities?q=<word>` returned the entity, because the server's `$or` has always matched `blocks.data.markdown` too (`lib/searchFilter.js`). KOL-061's list projection then made the gap permanent — before it the browser at least *had* the text it was failing to search. The split is now by **what each side knows**: the keyword goes to the server, which knows block content, and the category and tag pills stay in the browser, which already holds every listed row's category and tags — so a pill press during a search narrows the result set rather than costing a request. The request is **injected into `useFilters` at the WikiLayout call site** rather than imported by it, which keeps the composable reaching nothing by itself and lets its own tests drive the debounce, the race and the failure directly. Debounced ~250ms with a newest-response-wins guard (the same one `useEntityTypes` uses): an overtaken response must never replace a newer one. A **failed** request keeps the rows already on screen and raises a toast, because emptying the sidebar would read as "no matches" — an answer the server never gave. Because a match can now be invisible, a row whose term is in neither its title nor its summary carries a **"matched in text"** line; the client derives that **by elimination** rather than from a server hint, since the list response still carries no blocks, which is the cheaper half of the deal and needed no API change. The search request is deliberately **unpaged** (no `?limit=`, so the bare array, not KOL-067's envelope): a result set is a search's whole answer, and a page boundary would let a pill hide rows that exist. **Consequences:** `?q=` does not match tags where the old in-browser filter did, so typing a tag's name no longer finds a row on the strength of that tag alone — the tag pills are the exact-match path, and widening `keywordFilter` to tags (which would also widen the MCP and chat searches) is the follow-up if that is wanted; and a search result set does not refresh when the entity list does, so clearing the box is what returns the sidebar to the loaded list. Logging is `SEARCH_LOG_LEVEL` (`off | light | normal | verbose`, default `light`), whose light tier names each query's **source** — a typed term, a cleared box, a pill change — and every stale response discarded, because a debounced, raced, failable request leaves no other trace when a row that should be listed is not.
